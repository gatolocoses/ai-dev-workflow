# AGENTS.md — process contract

This file describes the **process**, not the product. It applies to every
contributor, human or AI. It changes only through the issue and pull request
flow below, with the owner's explicit approval.

Read `GOALS.md`, `HANDOFF.md` and `docs/decisions.md` before touching anything
that reaches the live system.

## 1. Issues first

- All work starts from an issue: one issue, one branch, one pull request.
- Before filing, verify the report against the current main branch. If it is
  already fixed, say so and do not file.
- An issue states the observed behaviour, the impact, and a direction for the
  fix. Refer to code by symbol name, never by line number.
- Labels: `severity:critical|high|medium|low`, `difficulty:hard|medium|easy`,
  plus `bug`, `enhancement` or `documentation`.

## 2. Origin tags

- Title prefix with your own model tag: `[<tag>] Short imperative summary`.
- Label: the same tag.
- Last line of the body, verbatim: `*Generated by <model id> — flag <tag>*`.
- Never use, rename or remove another agent's tag.

## 3. The gate

- Enable the hook once: `git config core.hooksPath .githooks`.
- The push gate runs: <list the exact commands here>.
- Quote the result (test counts and exit code) in the pull request body.
- Red means fix forward. Never merge red.
- `git push --no-verify` is for production emergencies only, and each use
  gets a follow-up issue.

## 4. Merge and deploy

- The owner decides what is merged and when it is deployed.
- Deploys happen only through `<deploy script>`. Merged does not mean live.

## 5. Execution discipline

- Zero deviations from the issue. If the work reveals a choice the issue did
  not make: for a small factual question, ask the owner; for a design
  question, build what the issue says, file the choice as a new issue, and
  note it in the pull request.
- Ask the owner with context and two or three concrete options, one marked
  **(recommended)**. Ask before doing the work that depends on the answer.

## 6. Size budgets

- New source files: <soft> lines means consider a split; <hard> lines is a
  hard stop.
- Files already over the budget may only shrink: <list them>.
- Measure with `wc -l`. Never quote a count in this file as current.

## 7. Landmine files

A second pass over the diff before pushing a change to any of these:

- `<file>`: <what breaks, and how it hides>

## 8. Debt

- Known shortcuts are issues labelled `DEBT`, each with one sentence on what
  it costs to leave.
- A debt issue becomes scheduled work after a production incident, or when
  two pull requests need to touch the same indebted code.

## 9. Definition of done

1. The issue is resolved, with no unrelated changes.
2. The gate is green on the committed diff, and the result is quoted.
3. A regression test covers the kind of defect that was fixed.
4. The documentation matches reality.
5. No secret or personal information entered git at any point.
6. The pull request body makes sense six months from now.

## 10. Keeping this file alive

Review this file when: an incident reached the live system; a rule was
followed and caused harm; a mistake happened because a rule was missing or
unclear. Every rule states its reason. A rule whose reason is gone is amended
or removed, never ignored.
